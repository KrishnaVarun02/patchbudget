# PatchBudget: focused literature and protocol review

Prepared 2026-10-01. This is a targeted primary-source review, not a comprehensive novelty search. No model API or paid service was used. The experiment design below is a recommendation, not a report of completed experiments.

## Closest precedents and defensible scope

| Work | Relevant established idea | Implication for a new local study |
|---|---|---|
| Qi, Mao and Lei, FRTP, ICSM 2013 | Update test priorities from failures observed during the repair search to reject invalid candidates earlier. | Include a failure-count scheduler; do not claim to invent adaptive patch validation. [Conference proceedings](https://icsm2013.tue.nl/ICSM2013.pdf), DOI [10.1109/ICSM.2013.29](https://doi.org/10.1109/ICSM.2013.29). |
| Yazhini, Phung and Lee, MPTPS, Applied Sciences 2020 | Prioritize by accumulated patch-killing counts per modification point and execute subsets until failure. | Modification-aware adaptive prioritization and sampling also predate PatchBudget. [Paper](https://www.mdpi.com/2076-3417/10/5/1593). |
| Spieker et al., RETECS, ISSTA 2017; Prado Lima and Vergilio, COLEMAN | Learn test priorities from execution history; COLEMAN explicitly uses bandits and time budgets in CI. | Bandit scheduling itself is established. CI cycles differ from a finite pool of alternative patches, which is a useful protocol distinction rather than sufficient novelty. [RETECS author PDF](https://hspieker.de/files/Spieker_et_al._-_2017_-_Reinforcement_Learning_for_Automatic_Test_Case_Prioritization_and_Selection_in_Continuous_Integration.pdf), [COLEMAN official conference page](https://2021.esec-fse.org/details/fse-2021-journal-first/31/A-Multi-Armed-Bandit-Approach-for-Test-Case-Prioritization-in-Continuous-Integration-). |
| Mündler et al., SWT-Bench, NeurIPS 2024 | Repository issue reproduction tests and generated-test filtering of candidate repairs. | Tests as a patch filter are established; a mutation study cannot claim a SWT-Bench result or LLM-agent result. [Official proceedings](https://proceedings.neurips.cc/paper_files/paper/2024/hash/94f093b41fc2666376fb1f667fe282f3-Abstract-Conference.html), [official harness](https://github.com/logic-star-ai/swt-bench). |
| Xiong et al., ICSE 2018; Ye et al., EMSE 2021 | Behavioral similarity for correctness assessment; independently generated tests using a human reference implementation as oracle. | Testing provides evidence of differences, not proof of general correctness. Reference-oracle access must be disclosed. [Xiong author preprint](https://arxiv.org/abs/1706.09120), [Ye paper](https://link.springer.com/article/10.1007/s10664-020-09920-w). |
| Yu et al., 2018/2019 Nopol study | Generated tests can expose regressions while oracle limitations constrain detection of incomplete fixes. | State which input domains and assertions the oracle actually covers. [Author preprint](https://arxiv.org/abs/1810.10614). |
| Martinez et al., xTestCluster | Cluster plausible patches by their behavior on newly generated tests. | Behavioral grouping of patches is established, so do not present disagreement-based grouping as novel without a more exact comparison. [Author preprint](https://arxiv.org/abs/2207.11082). |

A defensible present artifact is **“PatchBudget: A Reproducible Controlled Study of Test Scheduling for Candidate-Patch Screening.”** Its contribution can be a transparent harness, controlled candidate pools, a budget protocol, and measured comparisons. A small hand-written or mutation-based benchmark supports a preliminary empirical report, not publication-ready claims of a new general repair algorithm. Report negative/tied results if obtained.

## Recent primary work worth acknowledging

- Ahmed et al., **TDD-Bench Verified** (2024 preprint), evaluates test generation from pre-resolution repositories and issue descriptions. [Paper](https://arxiv.org/abs/2412.02883).
- Khatib, Mathews and Nagappan, **AssertFlip** (2025; revised 2026), generates passing tests and inverts them to reproduce bugs. [Paper](https://arxiv.org/abs/2507.17542).
- Kusama et al., **Multi-SWT-Bench** (submitted 28 September 2026), extends issue-reproduction evaluation across eight languages. This is a preprint newly available at the time of review, not a peer-reviewed result claimed here. [Paper](https://arxiv.org/abs/2609.34752).

## Feasible benchmark choice

**QuixBugs is locally practical once downloaded.** It contains 40 short algorithm programs with single-line defects and Python/Java versions; these originated as human programming challenges, not historical bugs from maintained production repositories. The repository includes corrected Python implementations and tests, so a Python-only adapter can avoid Java build tooling. Some routines need special graph inputs and some tests are slow; selection should use a declared mechanical criterion (for example JSON-serializable pure functions), with every exclusion recorded. [Original paper](https://jkoppel.github.io/QuixBugs/quixbugs.pdf), [repository usage](https://github.com/jkoppel/QuixBugs).

The repository has an MIT-style [LICENSE](https://raw.githubusercontent.com/jkoppel/QuixBugs/master/LICENSE). It also publishes [legal_notes.txt](https://raw.githubusercontent.com/jkoppel/QuixBugs/master/legal_notes.txt) describing uncertainty around historical Quixey rights. Preserve both notices if vendoring; do not claim an independent legal clearance. The present attempt to clone in the sandbox failed DNS resolution, so no QuixBugs execution was performed by this review agent.

For stronger external validity, **BugsInPy** contains historical Python project bugs but requires checkout/build dependencies and per-project environment setup. Its [official harness](https://github.com/soarsmu/BugsInPy) supports Docker and test execution; its [paper](https://arxiv.org/abs/2401.15481) reports 493 bugs from 17 projects. That is a later extension, not an implicit claim that this environment has already executed it. SWT-Bench similarly requires Docker/repository environments. Neither should be used as a result label without running the actual harness and reporting IDs.

## Recommended low-cost executable protocol

1. Fix a set of pure Python functions and valid input domains before evaluating policies. Freeze source hashes, benchmark commit, mutation operators, RNG seeds, exclusions, and budgets.
2. Generate executable candidate variants using deterministic AST mutations, retaining the reference implementation as an explicitly disclosed positive control. Call these *mutants/candidate variants*, not LLM patches. A reference positive control makes this a screening task with a planted solution; it is not evidence of repair-generation ability.
3. Filter candidate variants with a small shared public suite to obtain plausible candidates. Record all filtering cost separately from the scheduling budget. Report both number produced and number surviving. Avoid keeping only easy-to-distinguish variants based on the final holdout.
4. Separate tests into public screening tests, policy-accessible probe tests, and final held-out evaluation tests, with independent seeds and no exact input overlap. Keep final labels unavailable to scheduling, stopping, candidate generation, hyperparameter choice, and tie-breaking.
5. If the reference generates expected probe outputs, label the design **reference-oracle-assisted screening**. This is appropriate for a controlled experiment but unrealistic for unresolved issues where the correct implementation is unknown. Keep oracle execution cost visible.
6. At each budget unit, execute one (candidate, probe-test) pair. Reject a candidate immediately upon a valid failure; do not continue charging it unless the policy explicitly investigates failures. Identical candidates and shared tests still incur execution cost unless an explicitly justified caching model is shared by all policies.
7. Compare uniform candidate round-robin with random test order, candidate-sequential random testing with early stopping, static test priorities estimated from calibration candidates, and online failure-count priorities. A bandit variant may be added, but must beat these reasonable baselines, not only random unstructured sampling.
8. A policy may inspect only outcomes of previously charged executions plus genuinely available features. Precomputing the complete outcome matrix is fine for deterministic simulation **only if** the scheduler receives a query interface that reveals one charged cell at a time. Validate replay against actual executions and test that hidden-matrix changes do not alter a policy before affected queries are exposed.
9. Use the same candidate order, candidate pool, available probes, paired random seeds, budget, and candidate-selection tie breaker for every scheduler. Repeat random candidate orders: an accidental “correct candidate first/last” convention can dominate results.
10. At budget exhaustion report survivors and unresolved candidates. Selecting one survivor is not the same as verifying it. Record holdout error among survivors, false rejection of the reference, proportion of bad candidates rejected, count of candidate-test executions, and per-function selected-candidate holdout success. Show the budget curve and full-budget ceiling.

## Fairness and leakage pitfalls

- **Oracle leakage:** selecting tests by seeing their target-candidate failures, or computing information gain from the uncharged full matrix, is an oracle scheduler. It may be shown as an upper bound, never a deployable policy.
- **Calibration leakage:** use disjoint calibration and evaluation candidate pools. If both mutate the same source with the same operators, identify this as within-program transfer; it is not held-out-program generalization. A source-function split and an operator split are stronger sensitivity checks.
- **Count vs time:** fixed execution count controls queries, not wall-clock cost. Record both but do not translate query reduction into speedup when setup/coverage/oracle costs are omitted.
- **Input validity:** tests that violate documented preconditions can falsely reject equivalent patches. Exception handling and numerical tolerance must be explicit and consistent.
- **Equivalent mutants:** surviving all finite tests means “not distinguished by this holdout,” not semantically correct. Distinguish the known reference from surviving non-reference variants and report the equivalence limitation.
- **Dependence:** repeated random seeds on the same handful of functions are not independent research subjects. Aggregate per function first; use paired function-level comparisons/cluster bootstrap and display per-function results. Do not inflate sample size by treating every candidate-test cell as independent.
- **Tuning:** freeze policy parameters before final results. Any post-result tuning should be named exploratory and validated on a fresh split.
- **Scope:** results on a handful of pure functions do not establish performance on repositories, flaky tests, integration failures, generated tests, or autonomous coding agents.

## Follow-up for the implemented QuixBugs protocol

The parent task downloaded QuixBugs at commit `4257f44b0ff1181dedaedee6a447e133219fcebf`; this supersedes the availability limitation of this agent's failed clone attempt above. The parent plans AST single-edit variants plus the original bug and reference, with admission based only on provided developer tests. This is a suitable controlled screening protocol if original buggy variants that fail admission are recorded as excluded rather than silently retained.

The primary proceedings' indexed text exposes **FRTP Algorithm 1 on printed page 184**: the original failing test starts at index 1, passing tests at 0; each candidate runs tests in priority order; the first failure increments that test's index and causes a reorder by descending index with random ties; candidate validation stops at that failure. Passing all tests terminates repair. A probe-pool version with every index initialized at zero, fixed seeded tie priorities, and threshold acceptance differs in all three respects and should be called **FRTP-inspired failure-count ordering**. This is a precise, easily reproduced baseline, not an exact FRTP reproduction.

For this adaptation, let `h[t]` start at zero for every probe and select among tests unqueried on the current candidate by lexicographic minimum `(-h[t], random_tie_rank[t])`. Charge one execution, reveal that cell only, and add one to `h[t]` exactly when it rejects the current candidate. Share counts across candidates of this same function/run and reset at the next independent run. This recipe does not require a calibration matrix, execution-rate denominator, or reference-candidate identifier.

Use a two-by-two factorial comparison when possible: random versus history-based test ordering crossed with round-robin versus candidate-focused allocation. Apply an identical acceptance threshold and final selection tie-breaker across that comparison. A threshold can cause round-robin to abstain at small budgets because no candidate receives enough calls; report this as coverage/abstention, not automatically as reduced precision. Also report outcome without threshold to separate the effect of allocation from the effect of an acceptance rule. Count oracle construction and public-suite screening separately from candidate-probe calls; query reduction is not an established wall-clock speedup.
